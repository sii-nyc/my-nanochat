# Tokenizer 对比实验：2026-10-03

## 目的与设置

这次实验从同一份 ClimbMix 数据出发，**从头训练五个 byte-level BPE tokenizer**。一组固定 32K 词表，比较 1B、2B、3B 训练字符；另一组固定 2B 训练字符，比较 16K、32K、64K 词表。两组均保持文档顺序、`doc-cap=10000` 和预切分规则一致，因此可以分别观察训练语料量和词表大小的影响。运行命令为：

```bash
uv run python runs/tokenizer_experiment.py --run-id tokenizer-20261003 --no-upload
```

实验代码提交为 [`72b090b`](https://github.com/sii-nyc/my-nanochat/commit/72b090b1ca6a16bb0d8ac6fe8d98c179086ef477)。服务器共有 6542 个训练分片，按文件名排序，`shard_06542.parquet` 单独留作验证。1B、2B、3B tokenizer 实际分别读取前 5、9、14 个训练分片，数据哈希和全部运行配置见 [run.json](run.json)。训练产物、日志和离线网页留在 Git 忽略的 `training/tokenizer_experiments/tokenizer-20261003/`；这里保存的是可同步的实验报告。

所有 tokenizer 都通过了编码、解码往返检查。评估使用相同的新闻、韩文、代码、数学/LaTeX、科学文本，以及 ClimbMix 训练与验证分片各自的**第一个 row group**（各 1024 篇文档）。指标为 **BPT = UTF-8 字节数 / 普通 token 数**：同一文本的 BPT 越高，表示所需 token 越少。完整 BPT 表和切分结果见 [comparison.md](comparison.md)，精确 token 数和样本哈希见 [metrics.json](metrics.json)。`climbmix-train` 是训练数据样本；`climbmix-val` 来自留出的验证分片，但只覆盖其中一个 row group。

## 结果

| Tokenizer | 实际训练字符 | 词表大小 | BPE 训练时间 | 验证样本 BPT | 验证样本 token 数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `tok_1b_chars` | 1,000,001,077 | 32,768 | 55.84 秒 | 4.6892 | 645,016 |
| `tok_2b_chars` | 2,000,005,430 | 32,768 | 103.51 秒 | 4.6899 | 644,914 |
| `tok_3b_chars` | 3,000,005,961 | 32,768 | 156.47 秒 | 4.6901 | 644,895 |
| `tok_2b_vocab16k` | 2,000,005,430 | 16,384 | 102.23 秒 | 4.3946 | 688,246 |
| `tok_2b_vocab64k` | 2,000,005,430 | 65,536 | 101.16 秒 | 4.8791 | 619,914 |

固定 32K 词表时，从 1B 增加到 3B 训练字符，验证样本 BPT 仅从 **4.6892** 到 **4.6901**；同一段约 3.02 MB 的验证文本只少用了 **121 个 token**。新闻样本的 BPT 三组相同，其他小样本也没有一致的单调改善。这说明在**当前评估文本与规模范围内**，继续增加字符数带来的分词压缩收益很小，不能推断更多训练数据对模型学习没有价值。

固定 2B 训练字符时，验证样本 BPT 随词表从 16K、32K 到 64K 增长，依次为 **4.3946、4.6899、4.8791**。64K 相比 32K 在相同验证文本上少用 **25,000 个 token（约 3.9%）**。词表扩大对这次分词压缩的影响明显大于把 32K 词表的训练字符从 1B 加到 3B；但训练时间在三个 2B 实验中都约为 100 秒，不能仅凭这次 BPE 训练耗时判断后续模型训练的总成本。

定性切分与此一致。例如同一代码标识符 `parseHTTPResponse`，64K 词表能把 `Response` 合为一个 token，32K 将其拆为 `Resp` 和 `onse`，16K 则拆得更细。韩文样本在 16K、32K、64K 下的 BPT 分别为 **1.0531、1.1923、1.4834**；64K 有改善，但仍有不少字符被拆为不完整的 UTF-8 字节片段。单个片段不能独立解码是 byte-level BPE 的正常现象，拼接后仍可无损还原原文。GPT-2、GPT-4 的结果仅作为外部参照；它们的训练数据、词表和规则均不同，不能据此比较模型能力。

## 训练语料的语言构成

实验完成后，使用 [`scripts/tok_language_audit.py`](../../../../scripts/tok_language_audit.py) 与 fastText 语言识别模型对**这次 tokenizer 实际读取的文本**做了补充统计。脚本先核对 `run.json` 中前 14 个训练分片的哈希，再按训练时相同的文档顺序和 10,000 字符上限读取文本；每篇文档识别一个主要语言，并按文档截断后的 Python 字符数计算占比。3B 截止点的实际字符数与训练记录一致。

服务器上的复核命令如下。模型文件来源和语言代码见 [fastText 官方说明](https://fasttext.cc/docs/en/language-identification.html)，统计结果默认写到当前实验的 `public/language_audit.json`。

```bash
curl -fL https://dl.fbaipublicfiles.com/fasttext/supervised-models/lid.176.bin -o training/lid.176.bin
uv run --with fasttext-wheel==0.9.2 python -m scripts.tok_language_audit \
  --run-json training/tokenizer_experiments/tokenizer-20261003/public/run.json \
  --model training/lid.176.bin
```

| 训练字符预算 | 文档数 | 判为英语的字符占比 | 未判为英语的字符占比 | 识别置信度低于 80% 或空文本的字符占比 |
| --- | ---: | ---: | ---: | ---: |
| 1B | 379,436 | 99.953% | 0.047% | 0.632% |
| 2B | 758,523 | 99.952% | 0.048% | 0.639% |
| 3B | 1,138,013 | 99.955% | 0.045% | 0.643% |

3B 语料中，英语是 1,137,051 篇文档的主要语言；其余语言的字符占比都很小，其中德语约 **0.016%**、法语 **0.007%**、日语 **0.006%**、西班牙语 **0.006%**、韩语 **0.003%**，中文在打印精度下低于 **0.001%**。因此本次实验主要是在**英语语料**上训练 tokenizer；韩文等样本更适合用来检查非英语文本的切分与字节回退，而非证明多语言分词能力。

这些比例是语言识别器给整篇文档的**主要语言预测**，并非逐字符真值。低置信度比例与“英语 / 其他语言”预测**重叠**，不能相加；混合语言、代码和数学文本可能被误判。统计只覆盖本次使用的前 14 个训练分片，不能外推为整套 ClimbMix 的语言分布。完整 `language_audit.json` 保留在服务器的 `training/tokenizer_experiments/tokenizer-20261003/public/`；本节依据 2026-10-04 的服务器命令行输出记录。

## 结论与边界

这次受控对比表明：在当前验证样本上，**扩大词表能明显减少 token 数；增加 32K 词表的训练字符数收益很小**。结合语料审计，本轮结果主要描述英语导向 tokenizer 的行为。2B/32K 可作为后续基础模型训练的比较基线，64K 的 token 节省也值得在真实模型训练中衡量；本实验尚不能证明其中任何一个词表能带来更好的模型质量。

评估只用了一个验证 row group 和少数人工样本。BPT 不衡量模型损失、生成质量、推理延迟，也不包含更大词表可能增加的嵌入层与输出层开销。进入模型训练时，应固定并保存所选 tokenizer，再用下游训练和评测结果检验选择。
